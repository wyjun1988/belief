입력 요건(og_episode 출력이 이미 이 형식이어야 한다 — 아니면 먼저 맞출 것):

`--live-step 4`(신규)는 4장마다 1장만 SfM 에 넣는다. 등록 안 된 프레임은 평가에서 기하 기권이라 안전하고, 커버리지는
원본 프레임 수 기준으로 보고된다. **다음 20채 생성부터는 1,200~2,000 프레임으로.** (매핑워크는 무겁게 그대로.)

**(2) PyPI pycolmap 에 CUDA SIFT 없음 — 맞다.** CPU 로 계속해도 되지만, 그렇다면 **GPU1 은 §2-d(VGGT)에 쓰는 것이 낫다**.
근거: HSSD 20채에서 COLMAP 은 6채만 정렬됐고 실패 14채는 전부 **질감 많은 집의 지도 접힘**이었다(§153). OG 는 더
사실적인 렌더라 같은 실패가 예상된다. 즉 CPU COLMAP 은 *기준선*으로만 돌리고, 같은 4채에 VGGT(GPU)를 붙여 §2-d 표를
만드는 편이 정보량이 크다. 우선순위: **VGGT > CPU COLMAP 완주 > MASt3R-SLAM > CUT3R**.
(굳이 COLMAP GPU 가 필요하면 conda-forge `colmap` CUDA 빌드를 CLI 로 쓰는 방법이 있으나, 위 이유로 권하지 않는다.)


### 2-e. VGGT 실행 어댑터 도착 (2026-09-04) — 문서 `docs/RTX_VGGT_SETUP.md`
피드백대로 어댑터가 없어 자동 실행이 안 됐다. 이제 있다:

pycolmap 4.2 호환 수정은 서버 작업본 것을 **패치로 보내 주면** 본 저장소에 반영하겠다(우리 쪽은 3.13 로 검증돼 있다).

### 0-e. 🔴 최우선 — 매핑워크를 **자연스럽게 걷는** 촬영으로 다시 만들 것 (2026-09-04)
COLMAP 도 VGGT 도 OG 4채에서 무너진 **공통 원인**을 찾았다. 매핑워크가 *지점에서 제자리 회전*뿐이다(house_0000 지도 60장,
Pomaria 144장 = 18지점×8각). **제자리 회전은 시차가 없어 삼각측량이 불가능**하다. HSSD 에서 같은 매핑워크를 COLMAP 에
주면 128장 중 4~7장만 등록됐고, VGGT 는 지도 밀도를 3배 올려도 나아지지 않았다(회전 프레임만 촘촘해질 뿐).
SPEC 3-b(지점 사이 이동 프레임)가 og_episode 에 실제로 들어갔는지 확인해 달라 — 지도 장수가 `지점수 × 각도수` 와 같으면 안 들어간 것이다.

**해야 할 것 (live 는 그대로, `map/` 만 재생성):**
1. 매핑워크 = **사람이 폰으로 집을 한 바퀴 찍듯 연속으로 걷는 경로**. 모든 방을 지나는 하나의 경로(방 사이는 최단 경로),
   **0.3~0.4 m 마다 1장**, yaw 는 진행 방향, 회전은 한 프레임에 ≤25°(급회전 금지 — SPEC 4-4 와 같은 상한).
2. 방마다 2~3 지점에서 **추가로** 제자리 회전 45° 스텝(기존 방식) — 초기맵 검출용으로는 여전히 유용하다.
3. 결과 장수는 채당 **250~500장**이 정상(경로 길이 60~120 m ÷ 0.35 m + 지점 회전). 60~144장이면 이동 프레임이 빠진 것.
4. `gt.json["map"][i]` 에 이동 프레임도 같은 형식(`apos`·`yaw`·`room`)으로 넣는다. 순서 = 촬영 순서(경로 순).
참고 구현: 우리 `scripts/hab_episode.py --map-travel 0.4` (탐욕 최근접으로 지점을 잇고 `ShortestPath` 를 0.4 m 간격 표본, yaw=진행방향).

**재생성 뒤 순서**: 4채 map 재생성 → §2 COLMAP(CPU, `--live-step 4`) 한 채만 다시 돌려 *map 등록 수*가 대부분으로 오르는지 확인 →
오르면 VGGT(13절 확정 설정) → 표. 20채 생성(§0-b)은 이 매핑워크로.

### 0-f. og_episode `--map-travel` 도착 (2026-09-04) — 이식 완료, 바로 쓰면 된다
`scripts/og_episode.py --map-travel 0.35`(기본 0.35, 0=끔). 지점 사이 `ng.route` 경로를 0.35 m 간격으로 표본해
**진행 방향 yaw**(`atan2(dy,dx)`, live 보행과 같은 규약)로 촬영하고 `gt.json["map"]` 에 같은 형식(+`travel: true`)으로 넣는다.
방 라벨은 구간 전반부=직전 지점 방, 후반부=목적지 방. 끝에 `mapping walk: N frames total, M travel frames …` 한 줄이 찍힌다.

**바로 할 것**: 4채 `map/` 재생성(live 는 유지 — 우리 hab_episode 의 `--remap` 같은 스위치가 og 에 없으면 전체 재생성해도 됨),
`M travel frames` 가 150 이상인지 확인 → §2 COLMAP 한 채(`--live-step 4`)로 *map 등록 수* 상승 확인 → VGGT.
20채 생성도 이 옵션으로. (직접 이식하지 않아도 된다 — 이미 들어갔다.)

### 2-f. CUT3R 준비 완료 (2026-09-04) — `docs/RTX_CUT3R_SETUP.md` · `scripts/cut3r_reloc.py`
VGGT 검증에서 확인된 사실: 부분 재구성을 이어 붙이는 방식은 안 되고, **한 좌표계에 프레임을 누적**해야 한다. CUT3R 이 그
구조다. 순위를 올린다: **VGGT 단일 전역 통과(13절) 와 CUT3R 을 같은 4채에서 나란히**. H100 이 있으면 CUT3R 은 거기서.

### 0-g. 회신 (2026-09-04) — 이동 프레임 "150장" 은 절대 기준이 아니다, 그대로 진행
Rs_int 결과(map 180 = 회전 120 + 이동 60 · 경로 25.0 m · 0.35 m 간격)는 **정상**이다. 150 은 경로 60~120 m 짜리 큰 집의 기대치였고
25 m 씬에서는 나올 수 없는 수다. 기준을 상대값으로 고친다:
- **이동 프레임 ≥ 회전 프레임의 40%** 이고 **경로가 모든 방을 지나면** 통과 (Rs_int: 60/120 = 50% → 통과).
- 작은 씬은 `--map-sites` 를 3~4 로 올려 경로를 늘려도 좋다(회전 프레임도 늘어 초기맵에 유리). 필수는 아님.
그러니 **나머지 3채도 같은 설정으로 진행**해 달라. 참고: HSSD house_0000 에서 이동 프레임 60장만으로 COLMAP 지도 단독 등록이 4~7 → 14,
live 등록 978 → 1057 로 올랐다(§156). 진짜 판정은 장수가 아니라 아래 둘이다:
1. §2 COLMAP(`--live-step 4`) 한 채: `map 재구성: 등록 N/180` — N 이 두 자릿수면 시차가 들어간 것.
2. `docs/RTX_VGGT_SETUP.md` 15·16절: `sfm_scale_da.py` 로 OG 상수 재보정 → 질의 프레임 전역 통과 → GT sim3 진단 한 줄.

### 0-h. 2채 품질 확인 (2026-09-04) — Merom 기다리지 말고 **이 2채로 재국소화·평가까지** 진행
