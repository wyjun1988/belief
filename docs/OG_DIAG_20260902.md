## 2. 원인 1 (근본): USD 카메라 규약 — "안정적인 yaw"는 바닥샷이었다

USD 카메라는 **local −Z 를 바라보고 local +Y 가 up**이다. OmniGibson 스테이지는
z-up 이므로 **단위 쿼터니언 = 수직 아래(−Z world) 응시**다. 기존 코드의

```python
cam.set_position_orientation(position=[x,y,1.5], orientation=[0,0,sin(yaw/2),cos(yaw/2)])
```

는 world-Z 축 회전만 곱하므로 **영원히 바닥을 본다.** 실제 렌더 프레임을 열어
확인했다(`og51_probe_20260902/frames/000005.jpg` = 순수 마룻바닥).

이 하나로 세 증상이 동시에 설명된다.

1. **yaw 기하 검증 median 50°** — 아래를 보는 카메라에는 screen-x ↔ 방위각 관계가
   없다. 50°는 "규약이 어긋났다"가 아니라 "관계가 아예 없다"는 뜻이다.
2. **"단순 yaw 는 안정적"** — 1.5m 위에서 바닥 한 조각만 보므로 프러스텀 안
   프림·머티리얼·시맨틱 엔티티가 극소수다. 렌더러가 부담을 안 받는다.
3. **"수평 pose 를 주면 18~22 프레임에 죽는다"** — 수평으로 돌리는 순간 집 전체가
   프러스텀에 들어오고, 시맨틱 엔티티 수가 폭증한다 (§3).

### 고침 (검증됨)

```python
BASE = np.array([0.5, -0.5, -0.5, 0.5])   # (x,y,z,w): local −Z → world +X, local +Y → world +Z
q = qmul(yaw_quat_about_world_z(yaw), BASE)          # yaw=0 → +X 를 향한 진짜 수평
q = qmul(q, pitch_quat_about_local_x(pitch))         # 필요하면 국소 pitch
```

`scripts/og_pose_verify.py --scene Rs_int --n 40` 실측:

```
intrinsics W=1280 H=720 focal=17.0 h_aperture=20.995  fx=1036.437
quat_readback_max_err   0.0            ← 심이 우리가 준 값을 그대로 보관
projection_vs_depth     80/93 (0.860)  median |err| 0.077 m, signed −0.046 m
yaw_audit               screen_x_sign −1, yaw_offset 0.0°,
                        median_abs_error 0.0°, median_signed_error 0.0°
```

**SPEC §5 요구("오차 중앙값 0°")를 숫자로 통과.** 기존 50° → **0.0°**.
`screen_x_sign = −1` 은 기하적으로 필연이다: forward=+X, up=+Z 이면 right=−Y 이므로
화면 오른쪽으로 갈수록 방위각이 **감소**한다(habitat §120 과 같은 왼손 화면).
`scene_meta.screen_x_sign` 에 명시적으로 기록한다.

projection_vs_depth 의 median signed −0.046 m 는 AABB **중심**을 투영해 **앞면**
깊이와 비교하기 때문에 생기는 정상 편향이다. 큰 가구에서 커지므로 프레임마다
물체별 잔차를 `live[].occl` 에 남겨 감사 가능하게 했다.

## 3. 원인 2: segfault 는 세그멘테이션 annotator 그래프다 (depth 는 무죄)

`scripts/og_render_probe.py` 로 **한 번에 한 요인만** 바꿔 150 pose 씩 격리 측정.
각 config 는 별도 프로세스 (crash 가 다음 config 를 오염시키지 않게).

| # | modality | 시점 | get_obs | 완주 pose |
|---|---|---|---|---|
| A | `rgb` | 수평 | O | **150/150 + DONE** |
| B | `rgb+depth_linear` | 수평 | O | **150/150 + DONE** |
| C | `rgb+seg_semantic` | 수평 | O | **6** |
| D | `rgb+seg_semantic+seg_instance` | 수평 | O | **7** |
| E | `rgb+seg_semantic+seg_instance+depth_linear` | 수평 | O | **4** |
| F | E 와 동일 | **아래(기존 버그 pose)** | O | **150/150 + DONE** |
| G | E 와 동일 | 수평 | **X (get_obs 미호출)** | **6** |

읽는 법:

- **`seg_semantic` 하나만으로 죽는다.** `seg_instance` 특정 문제도, `depth` 문제도 아니다.
  (사용자 가설 5 는 depth 를 의심했지만 depth 는 150/150 완주.)
- **G 가 죽는다 = `get_obs()` 없이도 죽는다.** 원인은 데이터 fetch 가 아니라
  **매 render tick 마다 도는 annotator OmniGraph** 다. 스택트레이스와 일치:
  ```
  SyntheticData.py:1504 _post_process_graph_tick  →  graph.evaluate()   (ONDEMAND 그래프)
    ← simulation_context.render()  ←  og.sim.render()
  직전 경고: OgnSdInstanceMapping missing valid input renderVar InstanceMappingInfoSDhost
  ```
- **F 가 완주한다 = pose 자체가 아니라 프러스텀 안 내용물의 문제.** 바닥만 보면
  시맨틱 엔티티가 몇 개뿐이라 살아남고, 집 전체를 보면 죽는다. 그래서 재현이
  "18~22 프레임" 처럼 확률적으로 보였다.
- A/B/F 의 `rc=139` 는 **DONE 을 찍은 뒤** 종료 시점 segfault 다
  (`--/app/fastShutdown=True`). 무해하지만 러너가 종료코드로 성공을 판정하면
  오탐하므로, `EPISODE_OK` 표준출력 마커로 판정해야 한다.

### 대응: 세그멘테이션을 아예 쓰지 않는다

SPEC §4.2 와 PORTING_CHECKLIST 가 이미 요구하는 방향과 같다 —
**가시성은 depth 가 아니라 시선 레이캐스트로.**

| GT 항목 | 새 산출 방법 |
|---|---|
| `vis` | `og.sim.psqi` 레이캐스트(`omnigibson.utils.sampling_utils.raytest`). 눈 → 물체 AABB 중심 + 면중심 6점, 첫 충돌이 그 물체면 보임 |
| `ctr` | AABB 중심의 **해석적 투영** (fx = W·focal/h_aperture) |
| `box` | AABB 8꼭짓점 투영의 min/max, 프레임 클립 |
| `dist` | 수평 거리 (거리 컷 없음, `--vis-range 20`) |
| 가림 교차검증 | `occl = rendered_depth(u,v) − projected_z`, SPEC §4.2 의 ±0.6m |

비용: 프러스텀 통과 물체만 ×6 ray. Rs_int 61물체 기준 프레임당 수십 ray = 무시 가능.

> 이 경로가 **더 정확하다**는 점도 짚어둘 것: instance seg 는 픽셀 80개 미만이면
> 물체를 통째로 버렸다. 레이캐스트는 부분 가림에도 판정이 선다.

## 4. 원인 3: 배포된 navmesh 맵은 방마다 섬이다

`scripts/og_navmesh_audit.py` (Isaac 불필요, cv2 만) 로 51 씬 전수 측정.
OmniGibson 이 실제로 하는 처리를 그대로 재현 — 826px 원본을 0.1m/px 로
bilinear 축소 → `<255 → 0` → `cv2.erode`(`default_erosion_radius=0` 이면 0×0 커널이
되는데 OpenCV 가 기본 3×3 으로 처리하는 것까지 확인).

`Rs_int`, `floor_trav_0.png`:

```
컴포넌트 12개.  방별 소속:  bathroom→5  bedroom→3  entryway→6  kitchen→6  living→2
→ 어떤 단일 컴포넌트도 방 2개를 넘게 덮지 못한다
```

`floor_trav_no_obj_0.png`(가구 제거)조차 5방/5컴포넌트다. **문 통로가 맵 상에서
실제로 막혀 있다** — 21px(=21cm) dilate 해야 방이 붙는다. 해상도 축소 탓이라는
가설은 원본 0.01m/px 에서 재측정해 **기각**했다(결과 동일).

그래서 `scene.get_shortest_path()` 가 `None` 을 돌려준 것은 버그가 아니라
**데이터의 성질**이고, 맵을 고르는 것(`open_door`/`no_door` 변형)으로도 안 풀린다.

부수 발견: "가장 큰 컴포넌트"를 앵커로 쓰면 안 된다. `Rs_int`·`Wainscott_0_int` 는
**최대 컴포넌트가 집 밖 지면**이다(largest_frac 0.46~0.55, 그 안에 방 0개).
앵커는 **방을 가장 많이 덮는 컴포넌트**여야 한다.

### 고침: 라이브 씬을 레이캐스트해 navmesh 를 직접 만든다 (`scripts/og_navgrid.py`)

셀마다 머리높이(1.75m)에서 수직 아래로 ray 1발 → 첫 충돌이 바닥 높이면
**서 있을 수 있는 칸**. 그 뒤 0.25m 몸반경으로 erode, 4-연결 컴포넌트,
**방을 가장 많이 덮는 컴포넌트**를 선택, 그 안에서만 8-연결 A*(대각선 관통 금지).

측정 (0.05m 격자, 164×164 = 27k ray → **0.9초**):

| 씬 | 배포 맵 | 라이브 그리드 |
|---|---|---|
| `Rs_int` | 6 컴포넌트 / 최대 2방 | **5/5 방 한 컴포넌트** |
| `house_single_floor` | 21 컴포넌트 | **17/21 방** (`garage_0`·`garden_0` 포함) |
| `Ihlen_1_int` | 14 컴포넌트 / 4방 | 5/13 (2층 씬 — 위층은 floor 0 에서 정당하게 불가) |
| `Beechwood_0_int` | 14 컴포넌트 / 5방 | 3/11 ← 문 열기 부작용, 아래 참조 |

### 주의: 문을 무조건 열면 **더 나빠진다**

`Open.set_value(True)` 는 에셋 메타데이터가 지정한 방향으로 여는데, 그 문짝이
**통로 안으로 스윙**해서 서 있을 공간을 막는 경우가 있다. 실측:

```
Rs_int            문 닫힘 5/5  →  문 열기 4/5
Beechwood_0_int   (배포 open_door 맵 10/11) →  물리적 문 열기 3/11
```

그래서 `og_navgrid.open_doors_for_clearance()` 는 문마다 `shut / lower / upper` 세
관절값을 시도해 **문 주변 1.6m 안의 서있기 가능 칸이 최대가 되는 쪽**을 고른다
(문 개수 ≤15 × 3 후보 × 국소 패치라 비용 무시 가능).

## 6. 궤적 연속성 — 숫자로 닫음

"순간이동이 많고 회전이 빠르다"는 육안 지적을 실측으로 분해했다.

| 항목 | 1차 스모크 | 고침 후 |
|---|---|---|
| 프레임당 이동 median | 0.05 m (A* 셀 단위로 프레임화) | **0.242 m** |
| 프레임당 이동 max | — | **0.307 m** |
| 0.5 m 초과 점프 | — | **0 건** |
| prelude 길이(5방) | 335 프레임 | **89 프레임** |
| yaw 변화 median | — | 18.3° |
| yaw 변화 max | — | 174.7° → `--max-turn-deg 30` 으로 상한 |
| 45° 초과 프레임 | — | 33% → 상한 적용 후 0% |

즉 **위치 순간이동은 원래 없었다**(A* 경로만 따라간다). 육안에 점프로 보인 것은
(a) 영상 앞부분 **매핑워크**(설계상 6방향 스테이션 단위라 프레임 간 위치가 튄다)와
(b) 체류 스캔에서 위치가 고정된 채 시점만 60°씩 돌아간 것이다. (b)는 실제 결함이라
`limit_turn_rate()` 로 프레임 간 heading 변화를 30° 로 제한했다 — VO/SfM 포즈 사슬을
쓰려면 필수다. 감사에 `continuity` 블록으로 매 채 기록하고, 0.5 m 초과 점프가 하나라도
있으면 게이트 실패다.

## 7. 물체 부족 — BEHAVIOR 씬 내용만으로는 케이스 예산을 못 채운다

요건: **방 4~8개, 주방·화장실 포함**. `scripts/og_prescreen.py` (Isaac 불필요) 로
51 씬 전수 측정:

```
주방+화장실 있고 방 4~12개 : 14 / 51 씬
그중 "타입 유니크 + not fixed_base" 물체 수:
  Rs_int 9 · Rs_garden 7 · Beechwood_0_int 4 · Merom_1_int 4 · 나머지 ≤3
```

케이스 예산은 ②5 + ③5 + ④2 = **12건**이 필요하다. 최선의 씬조차 9개뿐이므로
**씬 내용만으로는 원리적으로 불가능**하다. 1차 스모크가 이걸 그대로 보여줬다:
`movable funnel {"non_structural":59,"unique_type":20,"not_fixed_base":9,
"in_reachable_room":9,"seen_in_mapping_walk":8,"carryable_size":4}` — 4개.

## 10. 범위 결정 (2026-09-02, 사용자 확정)

### 방: 4~8개, **주방·화장실 포함**

`scripts/og_prescreen.py` 로 51 씬 전수 측정 → **주방+화장실 있고 방 4~12개: 14 씬**.
`--min-rooms 4 --max-rooms 8 --need-types kitchen,bathroom` 로 코드에 게이트를 걸었고,
방이 넘치는 씬은 `NavGrid.restrict()` 로 **주방·화장실을 씨앗으로 인접 확장한 연결
부분집합**만 남긴다 (범위 밖 방으로는 경로도 내지 않는다).

### `garage` / `garden` 등 실외는 **범위 밖**

`EXCLUDE_ROOM_TYPES = garage · garden · porch · yard · lawn · balcony · patio ·
outdoor · driveway · deck · terrace` — 궤적·GT 방·이동 목적지 어디에도 들어가지 않는다.

**직접적 귀결: 경우④(집 밖 반출)는 목적지가 없어 생성이 불가능하다.**
`--case4` 기본값을 0 으로 내리고 `audit.case4_in_scope=false` 와
`outdoor_rooms_dropped` 를 기록한다. SPEC §1 의 "④ ≥2건" 은 이 범위에서 **충족 불가**다.

④ 를 살리려면 정의를 바꿔야 하는데, 범위 안에서 가능한 대안은 두 가지뿐이다 —
**둘 다 사용자 결정이 필요하므로 임의로 고르지 않았다.**

1. **범위 밖 방으로 반출**: 에피소드 범위(4~8방)에 들지 않은 방으로 옮긴다.
   "관측된 집에서 사라졌다" 가 성립하고 실외를 안 쓴다. 단 그런 방이 있는 씬에서만 가능.
2. **④ 를 폐기하고 ①②③ 만 쓴다**: 표본 예산이 ①10 · ②5 · ③5 = 20건/채가 된다.

현재 코드는 2번 상태로 돌고 있다 (`--case4 0`).

| 증상 | 원인 | 고침 |
