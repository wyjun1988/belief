# 점검 (2026-09-02) — 잘못한 것, 방향이 틀린 곳, 고칠 것

STATUS_20260902 는 "부품은 좋아졌고 제품 지표가 정체" 라고 썼다. 그 문서를 쓴 뒤
코드와 로그를 다시 뒤져 보니 **더 근본적인 문제가 셋** 있고, 셋 다 내 방법론 잘못이다.

## 한 줄 판정

**두 달간 알고리즘이 안 좋아진 게 아니라, 좋아졌는지 나빠졌는지 알 수 없는 방식으로
실험해 왔다.** 데이터·설정·GT 재료가 매번 같이 바뀌어 어떤 수치도 다른 수치와 비교가
안 된다. 이걸 먼저 고치지 않으면 OmniGibson 에서도 같은 두 달이 반복된다.

## 1. 내가 잘못한 것 (증거 포함)

### (1) "무GT" 라고 보고한 수치는 무GT 가 아니다 — 같은 실수 3번째
HSSD 0.489~0.511 을 "무GT 전체" 라고 썼다. 실제 재료:
| 재료 | 출처 | 근거 |
|---|---|---|
| 초기 씬그래프 | 검출 (무GT) | build_initmap |
| **카메라 yaw** | **GT** | 모든 HSSD 체인에 `LOC_YAW_GT=1` |
| **물체 거리** | **GT** | `GEO_DEPTH` 미설정 → `live.dist` 폴백 (eval_online:230) |
| 초기맵 구축 거리 | **GT** | build_initmap:83 `mp[k]["dist"]` |
| 가시성 | **GT** | eval_online:246(인스턴스 선택)·343(부재 기하) 가 `vis` 사용 |

정직한 이름은 **"검출 초기맵 + GT 포즈 + GT 거리"** 다. THOR 에서 실물 사슬(투표 yaw +
DA 깊이)이 오라클 0.975 → 실물 0.488 로 반토막 났던 것을 기억하면, HSSD 실물 수치는
0.49 가 아니라 **그보다 훨씬 낮을 것**이다. HSSD 에 실물 사슬을 안 붙인 이유(투표 yaw
오차 35.6°)는 "미해결" 로 적어 두고 GT 로 대체한 채 숫자를 냈다 — 사용자가 ①에서
지적한 것과 정확히 같은 구조의 실수를, 가드까지 만든 뒤에 다시 했다.

### (2) 고정 벤치마크가 없다 — 어떤 개선도 증명된 적이 없다
§101→§124 동안 평가 데이터가 바뀐 횟수: thor7(68) → 1024 → c3 → c3b → c3g →
ReplicaCAD → hssd20 → hssd20(매핑워크) → hssd20L → hssd20S. **열 번.**
알고리즘을 바꿀 때마다 데이터도 바뀌었으므로 "투영이 +0.20" 같은 주장은 전부
같은 판 안에서의 비교일 뿐, 판 사이에서는 성립하지 않는다. RESULTS 124절 중
**동결된 데이터에서 한 노브만 바꾼 대조 실험은 하나도 없다.**

### (3) 잡음을 신호로 읽었다
② n=27~40, ③ n=13~21, 집 20채. p=0.18·n=40 의 95% 신뢰구간은 **±0.12** 다.
그런데 결정을 내린 차이들: 0.489→0.494(인스턴스 채택), 0.583→0.551(융합 기각),
0.497→0.511(실검증). 전부 구간 안이다. "융합은 관측자 편향을 되살린다" 는 해석은
그럴듯하지만 **20채로는 검증 불가**였다. 실패 원리를 기록한 건 좋았으나 근거가 없었다.

### (4) 기준선을 나란히 두지 않았다 — 시스템이 단순 규칙보다 못한 곳이 있다
- 정지 지도(GT t=0) **0.684~0.695** > 기록(갱신 후) **0.299~0.500**.
  갱신 기계가 GT 정지 지도를 이긴 적이 없다. 무GT 비교로는 "초기맵만 답" 이 ≈0.45,
  시스템 0.49~0.51 → **갱신 기계 전체의 기여가 +0.05 안팎**이고 이것도 CI 안이다.
- T1(이동 후 새 방 목격) 에서 **단순 최신 강검출 0.312 > 시스템 0.000**.
  게이트·검증·합의를 다 거친 시스템이 "가장 최근에 강하게 잡힌 방" 보다 못하다.
이 두 줄이 매 보고에 있었어야 했다.

### (5) 포화된 노브를 몇 주 동안 못 봤다
후보 문턱 q0.80 은 §104 무렵부터 고정이었다. §112 에서 깊이 20→80 을 바꿔도
A 율이 안 움직였는데, 그때 "상류가 포화" 를 의심했어야 한다. §124 에서야 발견.
검증기 격자 5종(§112~118)은 **후보 단계에서 진짜의 80% 가 이미 잘린 뒤**의 실험이었다.

### (6) 설정 난립
eval_online 의 환경변수 노브가 수십 개고, 보고마다 조합이 다르다. "챔피언 설정" 이
동결돼 있지 않아 어떤 수치가 어떤 설정인지 로그를 뒤져야 안다.

## 2. 방향이 틀린 곳

### (a) 검증기로 쓰는 도구가 약하다 — 그리고 더 강한 도구를 이미 갖고 있다
VLM 2AFC(s_ab) AUC **0.78**, 기각 0.95 에서 진짜 수용 **0.24**. 후보에 진짜가 8장
있어도 6장은 버린다. 반면 exemplar 임베딩 검색(ax 캐시)은 AUC **0.93** 이다.
2AFC 는 "머그냐 컵이냐"(범주) 를 묻고, 우리가 필요한 건 "**그** 머그냐"(개체 재식별)다.
개체 재식별 도구(ax)를 후보 찾기에만 쓰고 채택 판정엔 안 썼다. **한 번도 비교 안 했다.**

### (b) ③ 을 시뮬 파라미터로 만들려 했다
"가장 먼 방으로 강제" 는 인위적이고 여전히 희귀했다(2~8%). 진짜 ③ 은 "서랍·가방에
넣었다" 이고 이건 수납을 시뮬하는 OmniGibson 이 아니면 안 만들어진다. HSSD 에서
③ 을 짜내려 쓴 시간(case3·far·에피소드 길이·LLM 시나리오)은 돌아오지 않는다.

### (c) 도메인을 4번 옮겼다
옮길 때마다 새 버그(좌표 규약·매핑워크·GT 오염 31%)를 늦게 발견했고, 그 사이 ②③
알고리즘은 한 줄도 안 바뀌었다. STATUS 에 이미 썼으니 반복 안 한다.

## 3. 잘한 것 (되돌리지 말 것)
- **투영 국소화 발견** — "보이는 방 ≠ 있는 방". 세 도메인 재현. 이 과제의 핵심 기술.
- **진단 도구** rtx7_diag·walksim — §124 는 이 도구가 만들었다. 가장 값진 엔지니어링.
- 실패를 지우지 않고 기록한 것. 단, 위 (3) 처럼 근거 없는 해석은 빼야 한다.
- 초기맵 투영·인스턴스 분리 — 원리는 맞다. 효과 크기는 재측정 필요.
