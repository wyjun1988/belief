# 갱신 트리거와 선택적 저장 — 설계 재검토 (2026-08-21)

인터뷰에서 나온 재설계. **셋이 한 덩어리**다: 트리거 · 저장 · 갱신.

## 문제 — 지금 설계가 막힌 자리

| 단계 | 지금 | 실측 |
|---|---|---|
| 갱신 | 씬그래프 물체마다 1fps DB 를 뒤진다 | **물체 300개 × 43,200프레임** — 하루 종일 못 끝낸다 |
| 질의 | 마지막 목격을 검색으로 찾는다 | **0.253** (상한 1.000) |
| 저장 | 원본을 버린다 | 나중에 seg·마스크를 다시 못 돌린다 |

## 재설계 — 장소 매칭을 트리거로

씬그래프를 만들 때 장소마다 **latent 키**를 남긴다. 기록 중 **30초 주기**로 현재
latent 를 구해 키와 대조하고, **매칭되는 순간이 키프레임**이다. 그때만 무거운 것을
돌려 갱신한다.

### 왜 나은가

**① 라우터 비용이 사실상 0** — 12시간에 1,440장 = CLIP 배치 19 ms/장 → **총 27초**.
(대안이던 손-물체 접촉 검출은 상시 모델이 필요해 비교가 안 된다.)

**② 사건이 아니라 상태를 본다.** "언제 놓았나" 를 짚을 필요가 없다:

| 관측 | 유도 |
|---|---|
| 조리대 방문 → 컵 없음 | 조리대에서 사라짐 |
| 싱크 방문 → 컵 있음 | 싱크에 생김 |
| 둘을 합치면 | **옮겼다** |

**re-ID 없이 옮김이 유도된다.** 부재 증거가 re-ID 대역을 한다는 것이 이 구조에서
자연히 작동한다.

**③ 0.253 실패를 우회한다.** 질의 때 "마지막 목격을 검색으로 찾는" 일이 없어진다 —
씬그래프가 이미 최신이므로 그냥 읽으면 된다.

### 위험 — 장소 매칭이 355곳 기준 top-1 **51%** 였다

트리거가 틀리면 엉뚱한 방의 상태를 써넣어 **그래프를 오염시킨다**. 갱신은 읽기가
아니라 **쓰기**라 오류가 누적된다.

다만 실사용 조건은 훨씬 유리하다:
- **집 필터** — 후보가 355곳이 아니라 그 집의 장소 몇 개
- **연속성** — 30초 전과 같은 장소일 확률이 높다(순간이동 안 한다)
- **자기검증** — 그 장소에 있어야 할 물체가 실제로 보이는지 확인할 수 있다

→ `scripts/hdepic_trigger.py` 로 셋을 하나씩 켜며 측정 중.
**90%대면 설계가 서고, 60%대면 못 쓴다.**

### 또 하나 — 같은 장소에 오래 있으면 중복 발화

부엌에서 30분 요리하면 60번 매칭된다. **진입 전이**나 **상태가 실제로 달라졌을 때**만
갱신해야 한다.

## 저장 — 1fps 는 유지하되 가지치기

⚠️ 라우터가 30초라고 기록도 30초로 줄이면 **안 된다.** 둘은 용도가 다르다:

| | 주기 | 용도 |
|---|---|---|
| 트리거 latent | 30초 | 갱신을 언제 돌릴지 |
| **1fps latent** | 1초 | **질의 응답 검색 풀** — "어제 저녁에 뭐 했지" |

**같은 트리거 신호로 버리기까지 판정한다**(사용자 제안) — 별도 로직이 없으니 비용이 0.
다만 매칭 실패를 그냥 "버려도 되는 것" 으로 보면 **모르는 장소가 영영 안 들어온다.**
새로 산 가구·가구를 옮긴 방·아직 안 가본 구석이 전부 매칭 실패인데, **물건을 어디
뒀는지 잊는 곳은 오히려 이런 데다**(늘 두는 자리면 안 잊는다). 그리고 씬그래프가
처음 만든 그대로 고정돼 자라지 못한다.

→ 판정을 **셋**으로 나눈다:

| 판정 | 처리 |
|---|---|
| **아는 장소에 매칭** | 살린다 → **갱신** |
| **매칭 실패가 지속**(예: 연속 3회 = 90초 이상) | 살린다 → **새 장소 후보** |
| 매칭 실패가 순간적 | 버린다 → 이동 중 |

"지속" 이 판별 기준이다 — 복도는 스쳐 지나가고, 새 장소는 머문다.

⚠️ 가지치기는 **검색 재현율을 깎을 수 있다.** 버린 프레임에 답이 있었으면 못 찾는다.
버리기 전에 **"버린 비율 대 hit@k"** 를 재야 한다 — 아직 안 쟀다.
(참고: 우리는 **반대 방향** 실패를 겪었다 — 풀이 3,106 → 10,891프레임으로 커지자
hit@5 가 0.75 → 0.30 으로 무너졌다. 가지치기는 풀을 **줄이는** 쪽이라 유리할 수도
있으나, 답이 든 프레임을 버리면 그대로 손해다. 방향이 반대이므로 재봐야 안다.)

## 선택적 원본 저장

키프레임에는 **원본을 남긴다**. 그러면 나중에 seg·마스크를 다시 돌릴 수 있어,
"원본을 버려서 마스크 앵커를 못 만든다" 던 벽이 사라진다.

예산: 지금 50 MB/12h. 키프레임이 하루 300장이고 장당 100 KB 면 **+30 MB** 로
두 배가 안 된다.

| 프레임 성격 | 남길 것 |
|---|---|
| **장소 매칭(키프레임)** | **원본 + 검출 메타 + latent** |
| 일반 | latent + 검출 메타 |
| 이동 중·정지 중복 | **버림** |

## 실측 — 트리거 정밀도 (P03 · 190회 · 장소 평균 8.4곳 · 우연 0.119)

| 방식 | 정확도 | 우연대비 |
|---|---|---|
| **단순 최근접** | **0.463** | 3.9배 |
| +연속성 | 0.468 | 3.9배 |
| +자기검증 | 0.458 | 3.8배 |
| 연속성+자기검증 | 0.468 | 3.9배 |

⚠️ **가산점 규모를 잘못 잡으면 크게 나빠진다.** 처음에 연속성 0.05·자기검증 0.02 로
줬더니 0.463 → **0.216** 으로 떨어졌다. 장소 키 간 유사도 차이가 **0.01~0.05** 뿐이라
가산점이 차이만큼 커서 **직전 장소에 고정**시킨 것이다. 1/50 로 줄이니 해가 사라졌다.

### 기대했던 세 조건이 모두 빗나갔다

"355곳 기준 51% 지만 실사용은 유리하다" 며 든 근거 셋:

| 조건 | 기대 | 실측 |
|---|---|---|
| 집 필터로 후보 축소 | 355 → 8.4곳이면 오를 것 | **46%** — 후보를 40배 줄여도 안 오른다 |
| 연속성(순간이동 안 함) | 크게 오를 것 | **+0.005** — 무의미 |
| 자기검증(물체 확인) | 오를 것 | **음수** — 키울수록 나빠진다(0.458→0.411) |

**후보 수 문제가 아니다.** 355곳에서 51%, 8.4곳에서 46% 로 사실상 같다.

자기검증이 해로운 이유는 짐작된다 — **부엌에서는 어느 가구 앞이든 비슷한 물체가
보인다.** 조리대 앞에서도 싱크와 냄비가 보인다. 변별이 아니라 잡음을 더한다.
이는 물체 조합 벡터(`owlvec`)가 장소 식별에서 우연 이하(0.9배)였던 것과 같은 원인이다.

## 1fps 가지치기 — **보류** (2026-08-21)

**다 저장하기로 했다.** 그러면 트리거의 성격이 바뀐다:

| | 버릴 때 | **다 살릴 때** |
|---|---|---|
| 트리거 실패 = | **데이터 소실**(복구 불가) | 계산 낭비(**다시 돌리면 됨**) |
| 맞는 지표 | top-1 정밀도 | **top-k 재현율** |
| 필요 수준 | 90%대 | 후보를 넉넉히 잡으면 됨 |

그리고 **예산을 다시 계산하니 여유가 있다** — 종전에 "OWL 전수는 24.5시간이라 불가"
라고 했는데, 하룻밤 8시간이면 **14,100프레임(전체의 33%)** 을 처리한다.
**30배가 아니라 3배**만 줄이면 되는 문제였다. 이 계산을 잘못 잡고 있었다.

→ 트리거는 **관문이 아니라 배분기**다. top-3 재현율이 80%대면 8.4곳 중 3곳만 처리해
3배 절감이 되므로 목표가 달성된다. 측정 중.

## ⚠️ HD-EPIC 은 **어안 미보정**이었다 (2026-08-21 · 사용자 지적)

브리스톨에서 받은 MP4 를 그대로 쓰고 있었는데, **1408×1408 원형 어안**이다.

| 검사 | 값 |
|---|---|
| 네 모서리 밝기 | **2 · 2 · 2 · 2** (중앙 146) |
| 판정 | **원형 어안 · 미보정** |

프레임을 직접 보면 조리대와 벽의 직선이 뚜렷이 휘어 있다.

### 왜 문제인가

**CLIP·OWLv2 는 일반 원근 이미지로 학습됐다.**

- 검은 모서리가 프레임의 **약 21%** — 정보 없는 픽셀에 표현 용량이 낭비된다
- 직선이 휘어 장면 구조가 달라진다
- **같은 장소도 시선 각도에 따라 왜곡 방향이 바뀌어** 임베딩이 흔들린다

마지막이 우리 문제와 직결된다. **시점 강건성이 계속 못 넘던 벽**이었는데(표현 7종
전부 시점여백 음수), 그 원인의 일부가 어안일 수 있다.

### 데이터셋별 실태

| 데이터 | 상태 |
|---|---|
| **ADT** | **rectify 함** — `aria_rgb_fisheye624 → linear` · 왜곡계수 0 |
| **HD-EPIC** | **미보정** — 1408×1408 원형 어안 |
| SceneDiff SD-K | HD-EPIC 유래 → **미보정 가능성 높음(미확인)** |
| SceneDiff SD-V | 폰·핸드헬드 → 보정 불필요 |

→ **HD-EPIC 수치(트리거 46% · 부재 0.585)가 어안 때문에 저평가됐을 수 있다.**
SD-K 가 SD-V 보다 부재 AUC 가 낮았던 것(0.557 vs 0.754)도 같은 원인일 수 있다.

### 대응

Aria 캘리브레이션은 `SLAM-and-Gaze`·VRS 에 있으나 받지 않았다. 캘리브레이션 없이도
**중앙 크롭**으로 검은 영역과 강한 왜곡부를 걷어낼 수 있다 — `--crop 0.7` 등.
크롭만으로 오르면 어안이 원인이고, 안 오르면 다른 문제다. 측정 중.
